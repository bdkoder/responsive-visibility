Visibility Conditions

This guide explains the server-side feature in Responsive Visibility. If you want a block to appear only for certain visitors, certain user roles, certain user IDs, or certain page types, this is the feature you use. The plugin does the checking for you and decides whether the block should be included in the final page.

This is different from device visibility. Device rules care about screen size. Visibility Conditions care about who is viewing the page and what kind of page it is. That distinction is important. A block hidden by device rules is usually still in the HTML and simply hidden with CSS. A block hidden by conditions is removed before the page is sent to the visitor. That makes conditions ideal for content that should not be shown at all unless the rule is met.

What you can control

The plugin includes a few common condition types that cover many real use cases. You can show content only when a user is logged in. You can target a user role such as Administrator, Editor, Author, Subscriber, or any custom role installed on the site. You can show a block for one exact user ID. You can target a specific post or page. You can also target a page type such as front page, blog page, single post, page, archive, search results, or 404 page.

  • Login Status for guest-only or member-only content.
  • User Role for role-based access and role-specific layouts.
  • Specific User for personal or account-based content.
  • Specific Post / Page for one exact page or post.
  • Page Type for broad page-context rules.

Depending on the site, these rules can be used for membership content, team-specific notes, special announcements, admin-only helper blocks, gated call-to-action sections, or page-specific messages that should only appear in one place.

How the panel works

Open the block in Gutenberg and find the Visibility Conditions panel. Turn on Enable conditions. After that, choose whether the block should be shown or hidden when the conditions match. Then add one or more conditions and choose whether all of them must match or any one of them is enough. This gives you a simple rule system without requiring code.

In plain language, the panel answers three questions. What do you want to do? When should it happen? Which condition or conditions should be checked? That is the whole system. You do not need to understand the code behind it to use it properly. You only need to know what content should be visible and under what rule.

  • Action decides whether the block is shown or hidden when the rule matches.
  • When decides whether all conditions or any condition must match.
  • Condition rows define the actual rule, such as logged in, administrator, or a specific user ID.

Why this is powerful

Visibility Conditions are powerful because they let you build content rules without extra plugins or custom templates. A membership site can show certain blocks only to members. A store can show special notes to customers. A blog can show admin-only helper content while the site is being edited. A landing page can hide a section from logged-out visitors until they sign in. These are common tasks, but they often become messy if you try to solve them with scattered code or page-specific hacks.

Because the rules run on the server, the result is cleaner than a simple visual hide. If a block should not be visible to a visitor, it does not need to be included in the page output. That is useful for privacy, cleaner HTML, and a more reliable user experience. It also helps reduce confusion when someone inspects the page source and wonders why the content is missing. It is missing because the rule said it should not be there.

How to use it step by step

  • Edit the page or post in Gutenberg.
  • Select the block you want to control.
  • Open the Visibility Conditions panel in the sidebar.
  • Turn on Enable conditions.
  • Choose whether the block should be shown or hidden.
  • Add one or more conditions.
  • Choose whether all conditions or any condition must match.
  • Save and test the result on the front end.

If you are new to conditions, start with one rule. For example, use Login Status and set it to Logged in. That is usually the easiest rule to understand because the result is immediate and obvious. After that, add a second rule if you need more precision. The plugin supports building up rules step by step, so you do not have to solve the whole problem at once.

Examples that make sense

  • Show a Family Pricing card only for logged-in users.
  • Show an admin note only for site administrators.
  • Show a private instruction block only for one team member with a specific user ID.
  • Show a message only on the home page or blog page.
  • Show a block only on one specific post or one specific page.

These examples cover the most common uses, but the real strength of the system is that you can combine rules in a way that matches the site you are building. If you need a block shown only when a user is logged in and has a certain role, the panel supports that kind of logic. If you want a block hidden when a rule matches, you can do that too. The point is to match the content to the visitor, not force every visitor to see the same thing.

Understanding the action setting

The action setting is easy to overlook, but it matters. If you choose Show this block, the block will appear only when the conditions are true. If you choose Hide this block, the block will disappear when the conditions are true. That gives you two different ways to think about the same rule. Sometimes it is easier to think in positive terms, like “show this only to members.” Other times it is easier to think in negative terms, like “hide this from guests.”

Both approaches work. Choose the one that makes the most sense for the people editing the content later. If your team reads “show this block” more naturally, use that. If they think in terms of hiding content, use that. Clear logic is more important than which wording you prefer.

Understanding all and any

The When setting controls how multiple conditions are combined. If you choose All conditions match, every rule must be true before the block is shown or hidden. If you choose Any condition matches, just one matching rule is enough. This is a simple but important difference. It lets you build either strict rules or flexible rules depending on what the page needs.

Example: Suppose you want a block to show only when the user is logged in and has the Subscriber role. That is an All rule. If either part is false, the block will not appear. But if you want a block to appear for users who are logged in or who are administrators, that is an Any rule. Understanding this difference will save you a lot of confusion while building complex pages.

Device rules versus conditions

It helps to repeat the difference one more time. Device rules are about size. Conditions are about visitors and page context. If the problem is “this block takes up too much space on mobile,” use device visibility. If the problem is “this block should only appear for logged-in users,” use visibility conditions. If the problem is both, use both.

For example, you could hide a pricing section on tablet with device rules and then show it only to logged-in users with conditions. That would let you control both the layout and the audience at the same time. The plugin is flexible enough to support that kind of combination without making the interface complicated.

Best practices

  • Start with one rule and test it before adding more.
  • Use clear condition choices so future editors can understand the logic.
  • Think carefully before hiding important content from visitors.
  • Use server-side conditions when the content should not appear in the page output.
  • Keep visitor rules separate from layout rules so the setup stays easy to read.

If you keep the rules simple and readable, they will be easier to maintain over time. That matters on real sites, where content often changes and the people editing the page later may not be the same people who created the rule in the first place. Good visibility rules should be obvious when someone opens the block panel months later.

Common mistakes and how to avoid them

  • Using a device rule when the real need is a user-based rule.
  • Forgetting to enable conditions before setting them.
  • Choosing the wrong action, such as hiding when you meant to show.
  • Setting a user role rule and then testing with the wrong account.
  • Building too many rules before testing the first one.

The easiest way to avoid mistakes is to test one condition at a time. Confirm that Login Status works. Then confirm that User Role works. Then try a specific user ID. Once the small tests are correct, combine them if needed. That keeps troubleshooting simple and prevents you from guessing which rule caused a problem.

Caching note

Since these rules are server-side, they behave differently from CSS-only device hiding. The plugin checks the visitor and page before the response is sent. That is why gated content stays out of the page source. On sites that use caching, the normal expectation is that logged-in and logged-out visitors are handled correctly by the caching layer. That is how most WordPress caching setups already work.

If you are working on a membership site, a store, or any site with access-controlled content, this distinction is worth understanding. The device feature is about the presentation layer. The conditions feature is about access logic. They are related, but they are not the same thing.

When to use conditions

  • When the block should only be visible to a certain kind of visitor.
  • When the block should depend on a logged-in state.
  • When the block should depend on a role or user ID.
  • When the block should appear only on one page or page type.
  • When you need the content excluded from the page for users who do not match the rule.

If you are unsure whether to use device visibility or conditions, ask one question: is the rule about the screen, or is it about the visitor? If it is about the screen, use the Responsive Visibility panel. If it is about the visitor or page context, use Visibility Conditions. That simple test will usually point you to the right tool.
