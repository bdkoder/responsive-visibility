Responsive Visibility Docs

This documentation is written for people who want a simple answer first: what does Responsive Visibility do, and why should I use it? In short, the plugin lets you control whether a Gutenberg block appears on a screen size, on a certain page, or for a certain user. That sounds technical, but the idea is easy. You decide when a block should be visible, and the plugin handles the rest.

Most WordPress sites do not need every block to appear everywhere. A big hero image may look perfect on a laptop but feel crowded on a phone. A secondary banner may help on desktop but get in the way on tablet. A pricing card may only matter for logged-in members. Without a tool like this, people often solve those problems with custom CSS, theme edits, page builder rules, or extra plugins. That works sometimes, but it is usually slower, harder to manage, and easier to break later.

Responsive Visibility keeps the control inside the block editor. That means the person building the page can make the decision right where the block already lives. No digging through theme files. No learning a custom coding system. No guessing how a rule will behave after the next update. The plugin is built to be practical: pick the block, choose the visibility rule, preview the result, and move on.

What the plugin is for

The plugin has two main jobs. First, it handles device-based visibility. That means you can hide a block on mobile, tablet, desktop, widescreen, or any other breakpoint you define. Second, it handles server-side visibility conditions. That means you can show or hide a block based on real logic such as login status, user role, a specific user, a specific page, or the kind of page being viewed. These two systems solve different problems, and together they cover most content visibility needs on a modern WordPress site.

  • Use device visibility when the layout should change by screen size.
  • Use visibility conditions when the content should change by visitor, page, or account.
  • Use both together when a block needs to be hidden on certain devices and also restricted by user state.
  • Use custom breakpoints when the standard mobile/tablet/desktop sizes are not enough.

What it is not

This plugin is not a full page builder. It does not replace Gutenberg, and it does not ask you to rebuild your site in a separate design system. It also is not a generic CSS framework. You are not writing your own media query rules for every block. Instead, the plugin adds a clean set of controls to the block sidebar and lets WordPress do the rendering work it is already good at. That makes the learning curve smaller and the result easier to maintain.

It is also not only for developers. The code behind the scenes is solid, but the user experience is meant for normal site owners, editors, content teams, and clients who just need a clear yes-or-no answer: should this block be visible here or not? If you can edit a block, you can use the plugin.

Why people use it

There are a lot of real-world reasons to hide or show blocks. A site owner may want to remove a heavy image on small screens so the page feels faster and easier to scan. A designer may want one layout on desktop and a simpler one on mobile. A membership site may want a call-to-action visible only to logged-out visitors. An online store may want to show different content to guests and subscribers. A company site may want a special message visible only to administrators while editing and testing pages.

These are not edge cases. They are normal parts of building a useful site. The challenge is doing it in a way that is easy to understand later. A lot of teams start with one-off CSS classes and custom conditions, then forget what each rule does after a few months. Responsive Visibility is meant to avoid that mess by keeping the rules attached to the block itself and labeling them in plain language.

How the plugin thinks about visibility

Think of visibility as a set of simple questions. Should this block be hidden on small screens? Should it show only for logged-in users? Should it appear only on this page? Should it show for this exact user? The plugin answers those questions for you. Device visibility is handled on the front end with CSS rules. Visibility Conditions are handled on the server before the page is sent to the visitor. That difference matters because it means each feature is doing the job it is best at.

The device tools are ideal when the content still exists on the page but should not appear on some screen sizes. The condition tools are ideal when the content should not be included at all for some visitors. If you understand that one distinction, the rest becomes much easier to use correctly.

Quick start

If you are in a hurry, here is the short version. Install and activate the plugin. Open any Gutenberg block. Use the Responsive Visibility panel to hide it on the screen sizes you do not want. If you need more control, go to the plugin settings and create custom breakpoints. If you need visitor-based control, open the Visibility Conditions panel and choose your rule. Save the page and preview it on the front end.

  • Want to hide a block on phones? Use device visibility.
  • Want to show a block only for members? Use visibility conditions.
  • Want to control both? Combine the two on the same block.

Recommended reading order

If this is your first time using the plugin, start with the device-based guide. That gives you the fastest win because the result is easy to see right away: hide a block on a screen size, preview it, and confirm the change. After that, read the conditions guide, because server-side visibility is more powerful and a little more abstract. Once you understand both, you will know which tool to use for each kind of problem.

Good ways to use it

  • Use it to reduce clutter on small screens.
  • Use it to show different calls to action to different visitors.
  • Use it to hide content that does not help a particular audience.
  • Use it to keep layouts simple without writing custom CSS for every section.
  • Use it to make pages feel more intentional instead of forcing every block to behave the same way everywhere.

Common mistakes

The most common mistake is using the wrong feature for the job. If a block only needs to disappear on a smaller screen, use the device controls. If a block should only be visible to logged-in users, use the conditions panel. Another mistake is hiding too many things at once. The plugin is helpful, but it should not be used to make a page confusing. If the content is important, make sure the reason for hiding it is real and useful.

Another common issue is forgetting to preview on the front end. The editor shows the controls, but the real test is the page itself. Finally, when using conditions, remember that login-based rules behave differently from device rules. Device rules are visual. Conditions are logical. Keeping that difference in mind prevents a lot of confusion later.

Before you move on

This plugin is designed to be useful without requiring you to become technical. You do not need to memorize CSS breakpoints or write custom PHP just to control a block. You only need to know what should be visible, when it should be visible, and who should see it. The next two guides go deeper into those decisions one at a time.

If you want the simplest path, read the device guide first. If you already know you need member-only or role-based content, go straight to the conditions guide. Either way, the goal is the same: make the page easier to use for the right people on the right screen.
